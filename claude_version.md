# C++ - разширени отговори за изпит (преработени обяснения)

Всяко обяснение по-долу използва думите от заглавието на точката, за да е ясно точно какво се обяснява. Където е полезно, има разширен, компилируем примерен код.

## 1. Обекти и класове. Дефиниция на клас. Общи понятия и концепции.

Класът представлява дефиниция на нов, потребителски тип данни, който обединява в едно цяло данните (данновите членове) и функциите (методите), които работят върху тях. Обектът е конкретна инстанция на класа — създаден по тази дефиниция екземпляр, който притежава собствено, независимо състояние. Основните понятия и концепции на обектно-ориентираното програмиране са капсулация, наследяване, полиморфизъм и абстракция: капсулацията скрива вътрешната реализация на класа зад публичен интерфейс, а абстракцията показва на потребителя само съществените поведения, без ненужни детайли.

```cpp
#include <iostream>
#include <string>

class User {
private:
    std::string name; // данен член - скрит чрез капсулация

public:
    User(std::string n) : name(n) {} // конструктор - създава обект по дефиницията на класа

    std::string getName() const { return name; } // метод - част от публичния интерфейс
};

int main() {
    User u("Ivan"); // u е конкретен обект (инстанция) на класа User
    std::cout << u.getName() << '\n'; // Ivan
}
```

## 2. Методи и параметри. Даннови членове и пропъртита.

Методите са функции, принадлежащи на класа, които описват поведението на неговите обекти, а параметрите, които им се подават, представляват входните данни, върху които методът работи. Данновите членове съхраняват състоянието на всеки обект и обикновено се декларират като private, за да не бъдат достъпвани директно отвън. В C++ няма вградена конструкция за пропъртита, каквато има например в C#, затова тяхната роля се изпълнява от двойка методи — getter и setter, — през които се чете и променя стойността на данновия член, при нужда с валидация.

```cpp
#include <iostream>

class Account {
private:
    double balance = 0; // данен член - вътрешно състояние на обекта

public:
    double getBalance() const { return balance; } // getter - имитира "четящо" пропърти

    void setBalance(double b) { // setter - метод с параметър, който валидира входа
        if (b >= 0) balance = b;
    }
};

int main() {
    Account acc;
    acc.setBalance(150.0);
    std::cout << acc.getBalance() << '\n'; // 150
}
```

## 3. Модификатори на достъп в клас.

Модификаторите на достъп определят откъде даден член на класа може да бъде видян и използван. public членовете формират публичния интерфейс на класа и са достъпни от всякакъв външен код; private членовете са видими само вътре в самия клас (и неговите приятели), а protected членовете се виждат и от наследниците му. Тези модификатори реализират капсулацията, като ограничават директния достъп до вътрешното състояние на обекта. Важна разлика между class и struct в C++ е нивото на достъп по подразбиране — private за class и public за struct.

```cpp
class Base {
private:
    int a; // видим само в Base

protected:
    int b; // видим в Base и в наследниците

public:
    int c; // видим навсякъде, част от публичния интерфейс
};
```

## 4. Accessor-методи. Mutator-метод.

Accessor-методът (getter) чете и връща стойност от състоянието на обекта, без по принцип да го променя, докато mutator-методът (setter) променя вътрешното състояние, обикновено след проверка дали новата стойност е допустима. Тази двойка методи е основният начин, по който клиентският код взаимодейства с private данните на обекта в C++. Чрез валидацията в mutator-метода класът пази своите инварианти — условия, които трябва да остават верни през целия живот на обекта.

```cpp
#include <iostream>

class Person {
private:
    int age = 0;

public:
    int getAge() const { return age; } // accessor - само чете

    void setAge(int value) { // mutator - променя, но с проверка
        if (value >= 0) age = value;
    }
};

int main() {
    Person p;
    p.setAge(25);
    std::cout << p.getAge() << '\n'; // 25
}
```

## 5. Методи на клас. Видове и модификатори. Припокриване.

Методите на един клас могат да бъдат обикновени (нестатични), const, static, virtual и други, като всеки модификатор променя семантиката им: const методът гарантира, че логическото състояние на обекта няма да бъде променено, а static методът принадлежи на класа като цяло, а не на конкретен обект, и затова няма достъп до нестатичните данни. Припокриването (overloading) означава дефиниране на няколко метода с едно и също име, но с различни списъци от параметри; компилаторът избира коя точно версия да извика според броя и типовете на подадените аргументи при компилацията.

```cpp
#include <iostream>
#include <string>

class Printer {
public:
    void print(int x) { std::cout << "int: " << x << '\n'; }
    void print(const std::string& s) { std::cout << "string: " << s << '\n'; } // припокриване по тип на параметъра
};

int main() {
    Printer p;
    p.print(5);        // избира версията с int
    p.print("hello");  // избира версията с std::string
}
```

## 6. Програмни практики: цифров часовник - диаграми на класове и обекти.

При проектирането на цифров часовник функционалността се разделя между няколко класа с ясно определени отговорности, например NumberDisplay (показва число в определен диапазон) и ClockDisplay (комбинира два NumberDisplay — за часове и минути). Класовата диаграма изобразява самите типове, техните атрибути, методи и връзките между тях на ниво дефиниция, докато обектната диаграма показва конкретни инстанции и стойностите им в определен момент от изпълнението на програмата. Разделянето на отговорностите по този начин позволява всеки клас да бъде разбиран, тестван и променян независимо от останалите.

## 7. Групиране на обекти. Колекции и итератори.

Групирането на обекти в програмата обикновено се реализира чрез стандартните колекции на C++ — vector, list, map, set и други, — всяка от които съхранява множество елементи по различен начин според нуждите на задачата. Итераторът е абстракция, която предоставя единен начин за последователно обхождане на елементите на дадена колекция, без клиентският код да зависи от нейната вътрешна реализация. В практиката range-based for цикълът е удобна синтактична обвивка, която вътрешно използва begin() и end() итератори на контейнера.

```cpp
#include <iostream>
#include <vector>

int main() {
    std::vector<int> nums{1, 2, 3};

    for (auto it = nums.begin(); it != nums.end(); ++it) { // явно използване на итератор
        std::cout << *it << ' ';
    }
    std::cout << '\n';

    for (int n : nums) std::cout << n << ' '; // range-based for - същото, но по-кратко
}
```

## 8. Проектиране на класова йерархия в обектно-структурирана програма.

При проектирането на класова йерархия общите характеристики на няколко сходни типа се извеждат в общ базов клас, а специфичното за всеки от тях поведение остава в съответните производни класове. Наследяване е подходящо да се използва само когато между типовете съществува истинска is-a връзка, а не единствено с цел преизползване на код. Добре проектираната йерархия позволява полиморфизъм през базовия тип и намалява дублирането, но прекомерното задълбочаване на йерархията може да я направи трудна за разбиране и поддръжка.

```cpp
#include <iostream>

class Animal {
public:
    virtual void sound() = 0; // чиста виртуална функция - прави Animal абстрактен базов клас
    virtual ~Animal() = default;
};

class Dog : public Animal { // Dog е в йерархия под Animal - истинска is-a връзка
public:
    void sound() override { std::cout << "Woof\n"; }
};

int main() {
    Dog d;
    Animal& a = d;
    a.sound(); // Woof - извиква се реализацията на производния клас
}
```

## 9. Оценка на качеството на кода. Свързаност и структурираност.

Оценката на качеството на кода често се базира на това доколко той е четим, лесен за тестване, промяна и повторна употреба, а не единствено на това дали работи правилно. Структурираността на дизайна се изразява чрез два взаимно свързани показателя: свързаност (coupling) между класовете и кохезия (cohesion) вътре в самия клас. Ниската свързаност означава класовете да зависят слабо един от друг, а високата кохезия означава всеки клас да съдържа само логически свързани отговорности — комбинацията от двете прави промените локални и намалява риска от странични ефекти при модификация.

## 10. Качество на код: дублиращи се фрагменти. Целево-ориентиран проект.

Дублиращите се фрагменти код влошават качеството на проекта, защото една и съща логика съществува на няколко места и всяка промяна в нея трябва да бъде повторена навсякъде, което лесно води до несъответствия. Типичното решение е общото поведение да бъде извлечено в отделна функция, метод или клас, към който се обръщат всички места, които преди са го използвали дублирано. В целево-ориентиран проект целта не е механичното премахване на всяко визуално сходство в кода, а избягване на дублиране на една и съща бизнес логика, която трябва да се поддържа консистентна.

## 11. Проектиране на обектно-структуриран код.

Проектирането на обектно-структуриран код започва с определяне на основните обекти в системата, техните отговорности, данните, които пазят, и начина, по който си взаимодействат помежду си. Всеки клас трябва да има ясно очертана роля и възможно най-малък публичен интерфейс, а детайлите по реализацията да остават скрити зад него. Зависимостите между класовете трябва да се поддържат минимални, като композицията (has-a връзка) често е по-гъвкав избор от наследяването, когато не съществува истинска is-a връзка между типовете.

## 12. Класове и обекти: разделяне на декларация и дефиниция. Създаване и унищожаване на обекти.

Разделянето на декларация и дефиниция на класа е стандартна практика в C++, при която декларацията (интерфейсът на класа — членове и сигнатури на методите) се поставя в header файл (.h/.hpp), а дефинициите на методите — в съответния .cpp файл. Този подход намалява зависимостите между отделните части на проекта и позволява header файлът да бъде включван на много места, без да се дублира реализацията. Създаването на обект става чрез извикване на конструктор, а при края на живота му автоматично се извиква деструкторът, който освобождава заетите от него ресурси.

```cpp
// User.h - декларация на класа
#include <iostream>

class User {
public:
    void hello(); // само сигнатура на метода
};

// User.cpp - дефиниция на метода
void User::hello() {
    std::cout << "Hello\n";
}

// main.cpp - създаване и унищожаване на обект
int main() {
    User u;    // конструктор по подразбиране - създава обекта
    u.hello(); // Hello
}              // тук се извиква деструкторът на u
```

## 13. Конструктори и деструктори. Видове конструктори.

Конструкторът е специален метод, който инициализира нов обект в момента на създаването му, а деструкторът се извиква автоматично при края на живота на обекта и освобождава заетите от него ресурси. В C++ различаваме конструктор по подразбиране (default), параметризиран конструктор, copy конструктор (създава обект от друг съществуващ обект) и move конструктор (премества ресурсите на временен обект вместо да ги копира). За разлика от обикновените методи, конструкторите не могат да бъдат обявени нито virtual, нито static, а при класове, участващи в полиморфна йерархия, деструкторът на базовия клас трябва да бъде virtual, за да се извика правилният деструктор на производния тип.

```cpp
#include <iostream>

class File {
public:
    File() { std::cout << "default ctor\n"; }
    File(const File& other) { std::cout << "copy ctor\n"; }
    File(File&& other) noexcept { std::cout << "move ctor\n"; }
    virtual ~File() { std::cout << "dtor\n"; } // virtual - за коректно полиморфно унищожаване
};

int main() {
    File a;                 // default ctor
    File b(a);               // copy ctor
    File c(std::move(a));    // move ctor
}
```

## 14. Дефиниране на връзки. Взаимодействия на обекти по вертикала и хоризонтала.

Връзките между класовете се дефинират в две основни посоки. Вертикалните връзки описват наследяването между базов и производен клас — връзка от тип is-a, изразена чрез синтаксиса `class Derived : public Base`. Хоризонталните връзки описват взаимодействие между независими класове чрез асоциация, агрегация или композиция, тоест обекти, които си сътрудничат, без единият да е специализация на другия. Във всички случаи обектите трябва да комуникират помежду си чрез публичните си методи, а не чрез директен достъп до вътрешните данни на другата страна.

## 15. Подтипове, подкласове и присвоявания. Предаване на параметри.

Подкласът наследява базов клас и може да бъде третиран като негов подтип, стига да спазва договора (интерфейса и очакваното поведение) на базовия тип — принцип, известен като заместимост на Лисков. При присвояване на производен обект по стойност на променлива от базовия тип възниква object slicing — специфичната част на производния обект се отрязва и се губи. Затова за коректен полиморфизъм при предаване на параметри трябва да се използва указател или референция към базовия тип, а не самия обект по стойност.

```cpp
#include <iostream>

class Animal { public: virtual void sound() { std::cout << "..."; } virtual ~Animal() = default; };
class Dog : public Animal { public: void sound() override { std::cout << "Woof"; } };

int main() {
    Dog d;
    Animal& a = d;   // референция към базовия тип - няма slicing
    a.sound();        // извиква Dog::sound() - полиморфизъм

    Animal byValue = d; // тук ИМА slicing - byValue е чист Animal
    byValue.sound();     // "..."
}
```

## 16. Наследяемост. Полиморфизъм. Достъп до методи и данни.

Наследяемостта позволява производният клас автоматично да получи членовете на базовия клас и да добави или преработи собствено поведение върху тях. Полиморфизмът позволява една и съща операция, извикана през указател или референция към базов тип, да изпълни различна реализация в зависимост от действителния (динамичния) тип на обекта по време на изпълнение. Достъпът до наследените методи и данни зависи както от модификаторите public/protected/private на самите членове, така и от вида наследяване (public, protected или private), с който е обявена връзката между класовете.

## 17. Виртуализация и реализация на полиморфизма. Абстрактни класове и виртуални функции.

Виртуализацията в C++ се постига чрез ключовата дума virtual, която кара компилатора да избира конкретната реализация на функцията по време на изпълнение (динамично свързване), вместо статично при компилация — това е механизмът, чрез който се реализира полиморфизмът през базова референция или указател. Абстрактен клас е клас, който съдържа поне една чиста виртуална функция (`= 0`) и следователно не може да бъде инстанциран директно, а само чрез своите производни класове. Производният клас реализира виртуалната функция чрез override, като при желание може изрично да извика и базовата реализация чрез `Base::method()`.

```cpp
#include <iostream>

class Shape {
public:
    virtual double area() const = 0; // чиста виртуална функция - прави Shape абстрактен
    virtual ~Shape() = default;
};

class Square : public Shape {
    double side;
public:
    Square(double s) : side(s) {}
    double area() const override { return side * side; } // реализация чрез override
};

int main() {
    Square sq(4);
    Shape& s = sq;
    std::cout << s.area() << '\n'; // 16 - извикано полиморфно чрез виртуализация
}
```

## 18. Вграждане на обекти. Copy-конструктори. Присвоявания и обекти.

Вграждането на обекти (композиция) означава един клас да съдържа обект от друг клас като свой данен член — връзка от тип has-a, а не is-a. Copy-конструкторът създава изцяло нов обект, копирайки състоянието на вече съществуващ, докато операторът за присвояване (`operator=`) променя съдържанието на вече съществуващ обект, замествайки предишното му състояние. При класове, които управляват собствени ресурси (памет, файлове и т.н.), трябва да се спазва Rule of 3 (или Rule of 5 с move операциите), а когато е възможно — предпочитаното Rule of 0, при което класът изобщо не управлява ресурси директно.

```cpp
#include <iostream>

class A {
public:
    A() = default;

    A(const A& other) { std::cout << "copy ctor\n"; } // нов обект от съществуващ

    A& operator=(const A& other) { // присвояване - променя вече съществуващ обект
        if (this != &other) {
            std::cout << "operator=\n";
        }
        return *this;
    }
};

int main() {
    A x;
    A y = x; // copy ctor
    A z;
    z = x;    // operator=
}
```

## 19. Референтни параметри. Работа с референции. Връщане на референции.

Референтните параметри позволяват на функцията да работи директно със съществуващ обект, без да създава негово копие. При работа с референции `T&` позволява промяна на оригиналния обект, а `const T&` дава достъп само за четене и е подходящо за подаване на големи обекти. Връщане на референции е безопасно само когато върнатата референция сочи към обект, който ще съществува и след приключване на функцията. Не трябва да се връща референция към локална променлива, защото тя се унищожава при излизане от функцията.

```cpp
#include <iostream>
#include <string>

void increment(int& value) {
    ++value; // Променя оригиналната променлива.
}

void print(const std::string& text) {
    std::cout << text << '\n'; // Само чете текста без копиране.
}

int& greater(int& first, int& second) {
    return first > second ? first : second;
}

int main() {
    int a = 3;
    int b = 8;

    increment(a);
    print("a = " + std::to_string(a));

    greater(a, b) = 10; // Променя по-голямата от двете променливи.
}
```

## 20. Конструиране на вградени обекти. Деструкция на вградени обекти.

Вградените (member) обекти вътре в един клас се конструират преди изпълнението на тялото на конструктора на съдържащия ги клас, тъй като първо трябва да съществуват в напълно инициализирано състояние. Редът на конструиране следва реда, в който данновите членове са декларирани в класа, а не реда, в който са изброени в member initializer list — затова инициализацията им обикновено се извършва точно чрез него. При деструкция на съдържащия обект вградените обекти се унищожават в обратен на конструирането ред — последно конструираният се унищожава първи.

```cpp
#include <iostream>

class Engine {
public:
    Engine() { std::cout << "Engine created\n"; }
    ~Engine() { std::cout << "Engine destroyed\n"; }
};

class Car {
    Engine engine; // вграден обект

public:
    Car() : engine() { std::cout << "Car created\n"; } // Engine вече е конструиран тук
    ~Car() { std::cout << "Car destroyed\n"; }
};

int main() {
    Car c;
} // ред на изход: Engine created, Car created, Car destroyed, Engine destroyed
```

## 21. Заделяне на обекти от динамичната памет.

Заделянето на обекти в динамичната памет традиционно се извършва с оператора new, а освобождаването — с delete, при което програмистът носи цялата отговорност за коректния момент на освобождаване. Неправилното управление на динамично заделени обекти води до типични грешки като memory leak (незаделена памет не се освобождава), dangling pointer (указател сочи към вече освободена памет), double delete (двойно освобождаване) и неясна собственост върху ресурса между различни части на кода. Модерният C++ предпочита RAII и smart pointers — unique_ptr и shared_ptr, — при които паметта се заделя и освобождава автоматично според живота на обекта, притежаващ указателя.

```cpp
#include <memory>
#include <string>
#include <iostream>

class User {
    std::string name;
public:
    User(std::string n) : name(std::move(n)) {}
    std::string getName() const { return name; }
};

int main() {
    auto p = std::make_unique<User>("Ivan"); // заделяне в динамичната памет
    std::cout << p->getName() << '\n';
} // delete не е нужен - паметта се освобождава автоматично при края на scope-а
```

## 22. Приятелски класове и приятелски функции. Статични членове на клас.

Приятелска (friend) функция или приятелски клас получава достъп до private и protected членовете на класа, без сам да бъде негов член — декларацията се прави чрез ключовата дума friend вътре в тялото на класа. Тъй като приятелството нарушава капсулацията, то трябва да се използва внимателно и само когато създава реална, обоснована зависимост между два класа. Статичните членове на класа принадлежат на самия клас, а не на конкретен обект — те са общи за всички инстанции и съществуват дори когато няма нито един създаден обект от класа.

```cpp
#include <iostream>

class Counter {
public:
    static int count; // статичен член - общ за всички обекти
    Counter() { ++count; }
};

int Counter::count = 0; // дефиниция извън класа

int main() {
    Counter a, b, c;
    std::cout << Counter::count << '\n'; // 3 - достъпен и без конкретен обект
}
```

## 23. Припокриване на оператори. Същност, ограничения.

Припокриването на оператори (operator overloading) позволява стандартни оператори като `+`, `==`, `<<` и други да получат смислена реализация за потребителски дефинирани типове, така че обектите да се използват също толкова естествено, колкото вградените типове. Съществуват съществени ограничения: не могат да се създават нови оператори, нито да се променят техният приоритет, асоциативност или броят операнди, с които работят. Добрата практика изисква реализацията на оператора да запазва естествения му, интуитивен смисъл — например `operator+` да връща нова стойност, а не да променя операндите си.

```cpp
#include <iostream>

struct Point {
    int x, y;

    Point operator+(const Point& other) const { // припокриване на оператор +
        return {x + other.x, y + other.y};
    }
};

int main() {
    Point a{1, 2}, b{3, 4};
    Point c = a + b; // естествена употреба благодарение на overloading
    std::cout << c.x << ' ' << c.y << '\n'; // 4 6
}
```

## 24. Преобразувания и операции-преобразувания.

C++ поддържа както неявни преобразувания, извършвани автоматично от компилатора, така и явни преобразувания, изразени с cast оператор. За явните преобразувания се използват `static_cast` (обичайни, проверени по тип преобразувания), `dynamic_cast` (безопасно преобразуване надолу по полиморфна йерархия), `const_cast` (премахва или добавя const) и `reinterpret_cast` (нискослойно преинтерпретиране на бита представяне), всеки предназначен за различна ситуация. Потребителските типове могат сами да дефинират операции-преобразувания чрез оператор conversion (например `operator int() const`) или чрез конструктор, приемащ единствен аргумент, което позволява обект от техния тип да участва в неявни или явни преобразувания.

```cpp
#include <iostream>

class Number {
public:
    operator int() const { return 42; } // операция-преобразуване към int
};

int main() {
    double d = 3.7;
    int x = static_cast<int>(d); // явно преобразуване

    Number n;
    int y = n; // неявно преобразуване чрез operator int()
    std::cout << x << ' ' << y << '\n'; // 3 42
}
```

## 25. CASE: обектно-структурирана програмна система - плащане.

В система за плащане обектно-структурираният подход въвежда обща абстракция Payment, която дефинира договора (интерфейса) на всички видове плащания, и конкретни реализации като CardPayment и BankPayment, които изпълняват този договор по свой начин. UML диаграмата на класовете описва съответните класове, техните методи, данни и връзките (наследяване, асоциация) между тях, като по този начин служи като план на системата преди самото ѝ имплементиране. Полиморфизмът позволява различните видове плащания да бъдат обработвани еднакво през общия интерфейс Payment, без извикващият код изобщо да се интересува от конкретния тип на плащането.

```cpp
#include <iostream>

class Payment {
public:
    virtual void pay(double amount) = 0; // договорът на абстракцията
    virtual ~Payment() = default;
};

class CardPayment : public Payment {
public:
    void pay(double amount) override {
        std::cout << "Card payment: " << amount << '\n';
    }
};

int main() {
    Payment* p = new CardPayment();
    p->pay(99.5); // Card payment: 99.5 - извикано полиморфно
    delete p;
}
```

## 26. Разширяване функционалността на системата за плащания: интерфейси.

Разширяването на функционалността на системата за плащания се постига чрез дефиниране на интерфейс — в C++ обикновено абстрактен клас с чисто виртуални функции и виртуален деструктор, — който описва какво трябва да умее всеки начин на плащане, без да задава как точно да го прави. Всеки конкретен клас за плащане наследява този интерфейс и предоставя собствена реализация на неговия договор. Благодарение на това нов начин на плащане може да бъде добавен само чрез нов клас, наследяващ интерфейса, без да се променя вече съществуващият код, който работи с абстракцията Payment — принцип, близък до Open/Closed.

```cpp
#include <iostream>

class Payment {
public:
    virtual void pay(double amount) = 0; // интерфейс
    virtual ~Payment() = default;
};

class BankPayment : public Payment { // ново разширение, без промяна на съществуващия код
public:
    void pay(double amount) override {
        std::cout << "Bank payment: " << amount << '\n';
    }
};
```

## 28. Софтуерни контракти. Пред- и пост-условия. Инварианти.

Софтуерният контракт на една операция се състои от предусловие — какво трябва да бъде вярно преди извикването ѝ (например валидни стойности на параметрите), — и постусловие — какво операцията гарантира след успешното си изпълнение. Инвариантът е условие, свързано със самия обект, което трябва да остава вярно през целия негов живот, независимо кой метод е извикан последно. Тези контракти правят изрична границата на отговорност между клиента (който трябва да спази предусловието) и реализацията (която трябва да спази постусловието), улеснявайки коректността и тестваемостта на кода.

```cpp
#include <stdexcept>

class Account {
    double balance;
public:
    Account(double b) : balance(b) {}

    void withdraw(double amount) {
        // предусловие: amount > 0 и amount <= balance
        if (amount <= 0 || amount > balance) throw std::invalid_argument("bad amount");

        balance -= amount;
        // постусловие: balance е намален точно с amount
        // инвариант: balance >= 0 остава вярно след операцията
    }
};
```

## 30. Контракт и наследяване. Ограничаване на областта в дъщерен обект.

Когато производен клас участва в наследяване, той трябва да спазва контракта на базовия си клас, за да може обект от него коректно да замества базов обект навсякъде, където той се очаква (принцип на Лисков). Това означава, че производният тип не трябва да изисква по-силни предусловия от базовия и не трябва да предоставя по-слаби постусловия от неговите. Ако дъщерният обект ограничи областта от допустими случаи спрямо базовия (например приема по-малко валидни входове), полиморфният код, писан срещу базовия тип, може да престане да работи коректно, когато реално получи производния обект.

## 31. Обектен дизайн: SOLID, Open/Closed и Single Responsibility.

SOLID е набор от пет принципа за създаване на по-модулен, гъвкав и лесен за поддръжка обектен дизайн. Принципът Open/Closed изисква класовете да бъдат отворени за разширяване (например чрез наследяване или нови реализации на интерфейс), но затворени за модификация на вече съществуващия, проверен код. Принципът Single Responsibility изисква всеки клас да има една ясно дефинирана отговорност и следователно само една причина да бъде променян — когато клас изпълнява няколко несвързани роли, промяна в едната лесно засяга и другата.

```cpp
// Нарушение на Single Responsibility: един клас смесва две отговорности
class ReportBad {
public:
    void calculate();   // бизнес логика
    void printToPdf();  // форматиране и извеждане - различна отговорност
};

// Спазване на Open/Closed: нова фигура се добавя без промяна на съществуващия код
class Shape { public: virtual double area() const = 0; virtual ~Shape() = default; };
class Circle : public Shape { public: double area() const override { return 3.14; } }; // разширение, не модификация
```

## 32. Обектен дизайн: принцип на верижната отговорност.

Принципът на верижната отговорност (Chain of Responsibility) организира поредица от обработчици във верига, през която преминава заявката. Всеки обработчик решава самостоятелно дали да поеме обработката ѝ, или да я предаде на следващия обработчик във веригата. Така изпращачът на заявката не зависи от конкретен получател, а веригата може да бъде разширявана или пренареждана, без да се променя кодът, който я стартира.

```cpp
#include <iostream>
#include <memory>

class Handler {
protected:
    std::shared_ptr<Handler> next;
public:
    void setNext(std::shared_ptr<Handler> n) { next = n; }

    virtual bool handle(int request) {
        if (next) return next->handle(request); // предава нататък по веригата
        return false;
    }
    virtual ~Handler() = default;
};

class SmallHandler : public Handler {
public:
    bool handle(int request) override {
        if (request < 10) { std::cout << "Handled by SmallHandler\n"; return true; }
        return Handler::handle(request); // не може - предава нататък
    }
};
```

## 33. Обектен дизайн: double dispatch в run-time.

Double dispatch е техника, при която изборът на изпълняваната операция зависи не от един, а от два обекта — и двата участват в run-time избора на конкретния код, за разлика от обикновеното виртуално извикване, което отчита само типа на единия обект (`this`). В C++ double dispatch обикновено се реализира чрез комбинация от виртуални функции и шаблона Visitor, при който всеки посетен обект приема виртуален посетител и на свой ред извиква съответния му виртуален метод. Подходът е полезен, когато поведението трябва да зависи едновременно от конкретния тип на посетителя и от конкретния тип на посетения обект.

## 37. Lambda изрази. Функции-обекти и функции през указатели.

Lambda изразът е анонимна, callable функция, дефинирана директно на мястото, където се използва, без да е необходимо да получава собствено име. Тя може да прихваща (capture) променливи от заобикалящия я scope и на практика често замества малки functor класове (класове с претоварен `operator()`) или обикновени function pointers, като запазва краткост и локалност на кода. Lambda изразите се използват изключително често при STL алгоритми, callback функции и асинхронни задачи, където предаването на малко, еднократно поведение като аргумент е по-удобно от дефиниране на отделен именуван клас или функция.

```cpp
#include <algorithm>
#include <vector>
#include <iostream>

int main() {
    std::vector<int> nums{3, 1, 2};

    std::sort(nums.begin(), nums.end(),
        [](int a, int b) { return a < b; }); // lambda вместо отделна функция или functor

    for (int n : nums) std::cout << n << ' '; // 1 2 3
}
```

## 38. Синтактични елементи на lambda изразите в C++.

Синтаксисът на lambda израз в C++ е `[capture](parameters) -> return_type { body }`, като типът на връщаната стойност често може да бъде пропуснат и изведен автоматично от компилатора. Списъкът за прихващане `[=]` прихваща всички използвани в тялото външни променливи по стойност (копие), а `[&]` ги прихваща по референция (директен достъп до оригинала); възможно е и избирателно прихващане на конкретна променлива, например `[x]` по стойност или `[&x]` по референция. Параметрите в скобите след capture списъка работят по същия начин, както при обикновена функция.

```cpp
#include <iostream>

int main() {
    int n = 10;

    auto add = [n](int x) { return x + n; }; // [n] - прихващане по стойност
    std::cout << add(5) << '\n'; // 15

    auto addRef = [&n](int x) { n += x; return n; }; // [&n] - прихващане по референция
    std::cout << addRef(5) << '\n'; // 15, като променя оригиналното n
}
```

## 39. Lambda изрази в асинхронни изчисления. Определяне на типа.

Lambda изразите могат директно да бъдат подадени като задача към `std::async` или `std::thread`, което ги прави удобен начин за стартиране на асинхронни изчисления без нужда от отделна именувана функция. Всяка lambda получава уникален, генериран от компилатора closure тип, който на практика не може лесно да бъде изписан ръчно — затова за определяне на типа ѝ обикновено се използва `auto`. При прихващане по референция трябва да се внимава прихванатият обект да продължава да съществува през цялото време, докато асинхронната задача се изпълнява, защото иначе се получава dangling reference.

```cpp
#include <future>
#include <iostream>

int main() {
    auto future = std::async(std::launch::async, [] { // lambda като асинхронна задача
        return 42;
    });

    std::cout << future.get() << '\n'; // 42 - блокира до получаване на резултата
}
```

## 40. Стандартизирани средства в C++ за паралелизация.

C++ предоставя стандартизиран набор от средства за паралелизация, сред които `std::thread`, `std::async`, `std::future`, мютекси и други примитиви за синхронизация. `std::thread` представя отделна нишка на изпълнение и трябва коректно да бъде join-ната (изчакана) или detach-ната, преди обектът да бъде унищожен — иначе програмата аварийно спира. `std::async` от своя страна стартира задача (евентуално в отделна нишка) и веднага връща `std::future`, чрез който по-късно можем да получим резултата от изчислението.

```cpp
#include <thread>
#include <iostream>

int main() {
    std::thread t([] {
        std::cout << "Hello from thread\n";
    });

    t.join(); // изчаква нишката да завърши
}
```

## 41. Синхронизация при паралелни изчисления. Атомарни типове.

Синхронизацията при паралелни изчисления е необходима, за да се предотврати data race — едновременен, неконтролиран достъп на няколко нишки до едно и също споделено състояние. Атомарните типове, реализирани чрез `std::atomic`, предоставят вградени атомарни операции (например четене, запис, увеличение) за подходящи прости типове, без да е нужен изричен mutex. Типичен пример за приложение е брояч, който се увеличава безопасно едновременно от няколко нишки, без резултатите от отделните нишки да се "изгубят" един върху друг.

```cpp
#include <atomic>
#include <thread>
#include <iostream>

int main() {
    std::atomic<int> counter{0};

    auto worker = [&counter] {
        for (int i = 0; i < 1000; ++i) counter.fetch_add(1); // атомарна операция
    };

    std::thread t1(worker), t2(worker);
    t1.join(); t2.join();

    std::cout << counter << '\n'; // винаги 2000, без data race
}
```

## 42. Взаимни изключвания при паралелни изчисления и примитиви.

Взаимното изключване (mutual exclusion) гарантира, че само една нишка може да изпълнява защитен критичен участък от кода в даден момент от времето, докато другите чакат реда си. `std::mutex` е основният примитив за взаимно изключване в C++, а `std::lock_guard` и `std::unique_lock` управляват заключването и отключването му автоматично чрез RAII. Използването на RAII при мютекси е важно, защото значително намалява риска мютексът да остане заключен завинаги при преждевременен `return` или изключение вътре в критичната секция.

```cpp
#include <mutex>
#include <iostream>

std::mutex m;
int shared = 0;

void work() {
    std::lock_guard<std::mutex> lock(m); // RAII - заключва при създаване, отключва при излизане
    ++shared; // критична секция
}

int main() {
    work();
    std::cout << shared << '\n'; // 1
}
```

## 43. Условни променливи при паралелни изчисления.

Условната променлива (`std::condition_variable`) позволява на нишка ефективно да изчака настъпването на определено условие, без да заема процесора с активно въртящ се цикъл (busy waiting). Чакащата нишка временно освобождава асоциирания mutex, докато чака, и се събужда едва след като друга нишка извика `notify_one()` (събужда една чакаща нишка) или `notify_all()` (събужда всички). Типичен пример за приложение на условните променливи е моделът producer-consumer, при който консуматорът чака да се появят нови данни, произведени от друга нишка.

```cpp
#include <condition_variable>
#include <mutex>
#include <thread>
#include <iostream>

std::mutex m;
std::condition_variable cv;
bool ready = false;

void consumer() {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return ready; }); // чака условието, без busy waiting
    std::cout << "Consumed\n";
}

void producer() {
    { std::lock_guard<std::mutex> lock(m); ready = true; }
    cv.notify_one(); // събужда чакащата нишка
}

int main() {
    std::thread c(consumer);
    std::thread p(producer);
    c.join(); p.join();
}
```

## 48. Обекти в паметта - особености и програмни грешки.

Обектите в паметта могат да имат автоматичен (стек), динамичен (heap) или статичен живот, в зависимост от начина, по който са създадени, и този живот определя кога паметта им се заделя и освобождава. Типични програмни грешки, свързани с обекти в паметта, са достъп извън границите на масив или буфер (out-of-bounds), dangling pointers (указатели към вече освободена памет), use-after-free, неинициализирани указатели и memory leaks (незаделена, но вече ненужна памет). Използването на RAII, стандартните контейнери на C++ и smart pointers значително намалява риска от подобни грешки, тъй като автоматизира заделянето и освобождаването на ресурсите.

## 49. Управление на памет в Linux системи: служебни структури.

Адресното пространство на процес в Linux обикновено включва няколко области — code/text сегмент (изпълнимият код), data сегмент (глобални инициализирани данни), heap (динамично заделяна памет, която расте нагоре) и stack (локални променливи и извиквания на функции, който расте надолу). Динамичната памет на heap-а се управлява от allocator, който в C се вика чрез malloc/free, а в C++ — чрез new/delete, при което самият allocator поддържа служебни структури за проследяване на заделените и свободните блокове. Терминът `unlink()`, който понякога се среща в конспекти по темата, не е стандартен C++ механизъм за освобождаване на обекти, а вътрешна операция на конкретни allocator реализации, затова за точния му изпитен смисъл трябва да се следва самата лекция.

## 50. Препълване на буфер. Поглед отвътре.

Препълването на буфер (buffer overflow) възниква, когато програмата запише в даден буфер повече данни, отколкото неговият размер позволява, при което излишните байтове презаписват съседна памет отвъд границите на буфера. Погледнато отвътре, това може да повреди други променливи, вътрешни служебни структури на стека или дори контролни данни на изпълняваната програма, което да доведе до срив или до неочаквано поведение. Основната защита срещу препълване на буфер е стриктна проверка на границите при всеки запис, както и използване на по-безопасни C++ абстракции — `std::string` или `std::array` с проверени операции — вместо суров `char` масив с фиксиран размер.

```cpp
#include <iostream>
#include <string>

int main() {
    char buffer[8];
    // strcpy(buffer, "This is definitely too long"); // ОПАСНО - препълва buffer

    std::string safer = "This is definitely too long"; // безопасна алтернатива
    std::cout << safer << '\n'; // расте динамично, без препълване
}
```

## 51. Атака от тип „frontlink“.

В наличния конспект темата за атаката от тип frontlink е спомената само по заглавие, без придружаваща дефиниция или пример, върху които може надеждно да се стъпи. Тъй като точното техническо съдържание на тази атака (какво в конкретния служебен списък се манипулира и как) не е дадено в изходния материал, тук не е коректно да се съчинява обяснение, което да звучи правдоподобно, но да не отговаря на лекционния материал. За изпитния отговор по тази точка е нужно да се използва точната дефиниция и пример, дадени от преподавателя в лекциите по темата.

## 52. Double-free vulnerabilities.

Double-free уязвимост възниква, когато един и същ динамично заделен ресурс бъде освободен (`delete`/`free`) повече от веднъж, което води до undefined behavior. Двойното освобождаване може да повреди вътрешните служебни структури на allocator-а, което впоследствие може да бъде експлоатирано от атакуващ за манипулиране на паметта. Използването на RAII и smart pointers като `std::unique_ptr` предотвратява този проблем по конструкция, защото собствеността върху ресурса е ясна и той се освобождава автоматично точно веднъж.

```cpp
#include <memory>
#include <iostream>

int main() {
    auto p = std::make_unique<int>(5);
    std::cout << *p << '\n';
} // паметта се освобождава точно веднъж, автоматично - double-free е невъзможен тук
```

## 53. Динамично управление на памет в Windows.

Windows предоставя собствени механизми за виртуална памет и heap памет (например функциите от Windows Heap API), върху които в крайна сметка стъпват allocator-ите, използвани от приложенията. C++ програмите, изпълнявани под Windows, могат да разчитат на стандартните средства на езика (`new`/`delete`, `malloc`/`free`) или да посегнат директно към Windows API, когато им е нужен по-нисък контрол над динамичното управление на паметта. В обикновен, преносим C++ код обаче е предпочитано да се разчита на RAII, стандартните контейнери и smart pointers, вместо на платформено-специфични API извиквания.

## 54. Служебни структури в динамичния мениджмънт на паметта в Windows.

Heap manager-ът в Windows поддържа собствени служебни (метаданни) структури, чрез които следи кои блокове от динамичната памет са заделени и кои са свободни, за да може да ги преизползва ефективно при следващи заявки. Точните служебни структури и техният формат зависят от конкретната версия и вътрешна реализация на Windows heap manager-а и не са публично стабилен, документиран интерфейс. Повреда на тези метаданни — например чрез out-of-bounds запис, use-after-free или double free — може да доведе до срив на процеса или да бъде използвана за уязвимости в системата за динамично управление на паметта.

## 55. Препълване на буфер в Windows и атаки, базирани на това.

Препълването на буфер в Windows е същият по същество проблем, както и на друга платформа — запис извън границите на заделен буфер, — но последиците могат да засегнат специфични за Windows служебни структури в паметта или контролния поток на процеса. Съвременните защитни механизми на Windows включват DEP (Data Execution Prevention, забраняващ изпълнение на код в области, предназначени само за данни), ASLR (случайно разположение на адресното пространство), stack cookies (откриват презаписан стек преди връщане от функция) и Control Flow Guard (проверява валидността на индиректни извиквания). Тези механизми значително затрудняват успешната експлоатация на препълване на буфер, но правилното решение остава предотвратяването на самите грешки в управлението на паметта чрез внимателна проверка на границите.
